利用者が 2026-09-11 に提示したたたき台を、(1) Google の口コミポリシーと消費者庁のステマ規制に照合し、(2) 既存アプリ（seo-checker）にどう載せるかまで落としたもの。

## 1. サービスの定義（たたき台のまま。変更なし）

「AI が口コミを書く」サービスではなく、**「来店客が自分の体験を書きやすくし、店舗が顧客の声を先に受け取れる」**サービス。

店舗への約束は「口コミ数を増やす」ではなく「顧客の声を漏らさず拾い、その一部が口コミになる」。裏の主価値は **「口コミにならなかった不満が店舗にだけ届く」**（§5）。

この定義は Google のポリシーともステマ規制とも整合する。**ただし、たたき台の「来店客側の体験」の手順 3（AI が下書きを生成）と、店舗側設定の「トーン」「含めたいキーワード」は、この定義と食い違い、2025〜2026 年のポリシー改定で明確に禁止側に入った**（§2）。定義を守るなら、その 2 つを外す設計にする（§3）。

## 2. ポリシー照合の結果（2026-09-11 時点）

### 2.1 前提と出典の扱い

- このセッションの環境からは **Google のヘルプページ（support.google.com）と消費者庁（caa.go.jp）を直接開けない**（ネットワークポリシーで 403）。以下は Web 検索の要約と複数の解説記事の一致点に基づく。**着手前に利用者が原文で確認すること**（§9 の #1。URL は §10）。
- 対象: Google「マップ ユーザー投稿コンテンツ ポリシー」（禁止・制限コンテンツ、評価の操作、インセンティブ付き・偏った口コミ）、景品表示法「一般消費者が事業者の表示であることを判別することが困難である表示」（2023-10-01 施行、いわゆるステマ規制）とその運用基準・Q&A。

### 2.2 確認できたルール

| 出典 | ルール | 影響する箇所 |
|---|---|---|
| Google（従来から） | 実体験に基づかない投稿、**インセンティブ（金銭・割引・無償提供）と引き換えの口コミ**、**レビュー ゲーティング**（満足した客だけに依頼し不満な客を別導線へ）は禁止 | 投稿導線の出し分け、特典 |
| Google（2025 年〜、解説記事の一致点） | **AI で生成した口コミ本文は、体験が本物でも削除対象**。Gemini による自動検出で 2025 年の削除件数が大幅に増加 | **手順 3 の AI 下書き** |
| Google（2025-10 〜） | 偽・インセンティブ付きの口コミについて、オーナーへ削除通知。プロフィールに「このビジネスはポリシーに違反している可能性があります」の警告、過去の口コミの一括削除も | 店舗が負うリスクの大きさ |
| Google（2026 年） | マップの利用者に **「このビジネスは口コミの見返りに特典を提供していますか？」（はい / いいえ / わからない）** と尋ねる。「はい」が集まると過去分も含めて削除 | アンケート謝礼の見せ方 |
| Google（**2026-04-17 改定**、「評価の操作」の節に追記） | **(a) 従業員に口コミの目標数（ノルマ）を課すこと**、**(b) 従業員名や特定の内容・キーワード・言い回しを含めるよう依頼すること**を明示的に禁止 | **含めたいキーワード設定、スタッフ別 QR** |
| 消費者庁 Q&A | 口コミ投稿の依頼で、**投稿内容の指示が無く、対価が割引程度**なら、通常「事業者の表示」に当たらない | アンケート謝礼 |
| 消費者庁 Q&A | **「星 5」を条件にする、品質・価格等を推奨するコメントを条件にする**と、事業者が表示内容を決定しているので「事業者の表示」に当たり、事業者の関与を明瞭にしないと違反 | AI 下書き、キーワード |
| 消費者庁 運用基準 | 事業者が第三者に依頼・指示するなど**表示内容の決定に関与**した場合は事業者の表示。「文案の提供」を名指しした記述は Q&A に見当たらないが、店舗の設定（店名・看板メニュー・トーン）を反映した文章を渡す行為は「内容の決定に関与」と読まれる余地が大きい | AI 下書き |

### 2.3 たたき台の各項目の判定

| たたき台の項目 | 判定 | 理由と対処 |
|---|---|---|
| QR → アンケート → 完了画面に Google 投稿ボタン | **OK** | 依頼自体は許容。内容に関与しない・全員に同じ導線、が条件 |
| 投稿ボタンは評価の高低に関わらず全員同じ | **OK（必須）** | ゲーティング禁止に適合。**ボタンの順序・大きさ・文言も評価で変えない**ことをコードで固定する（§3.3） |
| 低評価者に「お店に直接伝える」を並列追加 | **OK** | 隠さず選択肢を足すだけなら可。ただし「低評価のときだけ出す」のではなく **全員に出す**方が安全（低評価だけ導線が増える = 出し分け、と見られる余地を消す）。推奨: 全員に 2 ボタン、順序固定 |
| **AI が回答から口コミの下書きを生成し提示（編集可）** | **NG（外す）** | ① Google は AI 生成本文を削除対象にしており、ユーザーが編集せずそのまま投稿すると検出 → 削除 → 店舗に警告のリスク。② 店舗の設定を反映した文案 = 事業者が表示内容の決定に関与 → 景表法上「事業者の表示」となり、口コミ本文に「店舗の依頼で投稿」等の明示が要る（実質、口コミとして成立しない）。③ 編集可能でも「関与」は消えない。**代替は §3.2**（回答者自身の言葉をそのまま見せる） |
| 店舗側の「AI 生成のトーン設定」 | **NG（外す）** | 上と同根。下書きを外せば不要 |
| 店舗側の「含めたいキーワード（店名・看板メニュー）」 | **NG（外す）** | **2026-04 改定で名指しで禁止**（特定の内容・キーワードの依頼）。アンケートの質問文に「〇〇（看板メニュー）はいかがでしたか」と入れるのも同じ効果を持つので、**質問文は業種テンプレートの一般的な文言に限り、店舗は質問を追加できるが「口コミに書いてほしい語」を誘導する用途には使わない**旨を利用規約と管理画面に明記 |
| QR を店舗別・テーブル別・スタッフ別に発行 | **条件つき OK** | 店舗別・テーブル別・レジ別・時間帯別は経路分析として問題ない。**スタッフ別は、スタッフごとの回答数・投稿ボタン押下数を並べた時点で「ノルマ」に近づく**（2026-04 改定）。v1 では発行単位を「店舗・テーブル・レジ・その他（自由ラベル）」にし、**スタッフ名をラベルにする用途は案内で避ける**。要望が強ければ「スタッフ別は回答数のみ表示、投稿押下数は出さない」を条件に検討 |
| 口コミ投稿への特典は付けない | **OK（必須）** | Google・景表法の両方に適合 |
| 謝礼を出すなら「アンケート回答」に対して切り分ける | **条件つき OK。v1 では機能として提供しない**ことを推奨 | 景表法上は内容指示なし・割引程度なら可。しかし Google は 2026 年に**来店客本人に「特典があったか」を尋ねる**ようになったため、同じ画面の流れで謝礼と投稿ボタンが並ぶと来店客が「はい」と答え、店舗の過去口コミごと削除されるリスクがある。提供するなら (a) 謝礼はアンケート送信時点で確定・表示し、(b) Google ボタンは別画面（次の画面）に置き、(c) 謝礼の画面に Google の文字を出さない、(d) 案内文に「口コミの投稿とは無関係です」を固定表示。これを守っても来店客の受け取り方は制御できないので、**v1 は謝礼機能なし、店舗が独自に謝礼を配る場合の注意書きを説明資料に入れる**に留める |
| 生成文を店舗側がすべて閲覧できる | **OK（下書きを外すので「回答をすべて閲覧」になる）** | 回答は店舗宛のフィードバックなので閲覧は当然。**ただし「回答者 × Google に実際に投稿された口コミ」を突き合わせて投稿者を特定する機能は作らない**（口コミの匿名性・削除依頼の材料にしない） |
| 業種別テンプレートで「人間が書いた自然な体験の口コミになるように」 | **目的を変えて残す** | 「自然な口コミにする」ための文章テンプレートは AI 下書きと同じ問題。**「体験を思い出しやすい質問の並び」の業種別テンプレート**（§6）として残す。自由記述が増えれば、結果的に口コミも具体的になる |
| クリニック（業種） | **要追加確認** | 医療機関は医療法の広告規制（医療広告ガイドライン）で**治療内容・効果に関する体験談を広告に使えない**。口コミ依頼そのものは直ちに広告ではないが、クリニックが導線を用意して体験談を集める行為は、集めた声をサイト等に転載した時点で広告規制に触れる。**v1 の想定業種は飲食・サロンに絞り、クリニックは専門家確認後**を推奨 |

**結論**: たたき台の骨格（アンケート → 店舗にフィードバック → 全員同じ投稿ボタン）はそのまま使える。**外すのは「AI 下書き」「トーン」「キーワード」の 3 つ**、条件を付けるのは「スタッフ別 QR」「謝礼」「クリニック」。これで §1 の定義と完全に一致する。

## 3. 来店客側の体験（修正版）

### 3.1 流れ

1. 店内の QR コードを読み取る → `https://app.seo-checker.tokyo/r/<slug>`（ログイン不要、スマホ最適化）。
2. 店舗が設定したアンケートに答える（3〜6 問。評価スケール 1 問 + 選択式 1〜2 問 + 自由記述 1〜3 問。所要 1 分）。**自由記述は「良かった点」「気になった点」を分けて置く**（不満を書く場所を最初から用意する）。
3. 送信 → 完了画面:
   - 「ご意見をお店に送りました。ありがとうございます。」
   - **「あなたの回答」**: 自由記述の原文をそのまま表示し、「コピー」ボタン。AI による整形・言い換え・追記は**しない**（§2）。回答者が自分の言葉を口コミに流用するのは本人の自由。
   - ボタン 2 つ（**全員に同じ順序・同じ大きさ**）: 「Google マップに口コミを書く」「お店に直接伝える」。
4. 「Google マップに口コミを書く」→ Google の投稿画面へ（`writeAReviewUri`。Places API の `googleMapsLinks.writeAReviewUri` は r28 で取得済み。無ければ `https://search.google.com/local/writereview?placeid=<place_id>`）。押下は `navigator.sendBeacon` で記録してから遷移。
5. 「お店に直接伝える」→ 追加の自由記述 1 欄 + 任意の連絡先（メール or 電話、空でも送れる）。送信すると店舗の管理画面で「直接連絡あり」として上に出る。

### 3.2 「AI 下書き」を外した代わりに何で書きやすくするか

- 質問の並びで体験を思い出させる（§6 のテンプレート）。
- 完了画面で自由記述を**そのまま**見せて、コピーできるようにする。
- 「口コミの書き方のヒント」は、**Google 自身の一般的な案内の範囲**（「具体的に」「実際の体験だけ」「個人情報は書かない」）を固定文で出す。店名・メニュー名・スタッフ名の誘導はしない。

### 3.3 コードで固定する原則（テストで守る）

- 完了画面の 2 ボタンは評価値に関係なく**同じ配列・同じ props** で描画する（`rating` を受け取らないコンポーネントにする）。
- 完了画面と `/r/<slug>` の API 応答に「特典」「クーポン」「割引」を表す項目を持たせない（型に無い）。
- 店舗設定に「トーン」「キーワード」「口コミの例文」を保存する項目を作らない（zod スキーマに無い）。
- 質問文にスタッフ名を入れるのは技術的に止められないので、**利用規約と管理画面の注意書き**で担保し、説明資料に「なぜやらないか」を書く（§7）。

## 4. 店舗側の管理画面（`/tools/reviews`、有料）

### 4.1 設定

- **店舗の紐づけ**: MEO の登録店舗（`meo_stores` の自社店舗）から選ぶ。`place_id` と `writeAReviewUri` は保存済みの報告書から取る。
- **アンケートの編集**: 業種テンプレートから開始 → 質問の追加・編集・並び替え・削除（種類: 評価スケール 1〜5 / 選択式（単一・複数）/ 自由記述）。最大 8 問、自由記述は 500 文字。**1 フォームにつき評価スケールは 1 問**（低評価判定に使う）。
- **QR の発行**: 発行単位のラベル（店舗 / テーブル 3 / レジ / 会計伝票 など）を付けて複数発行。SVG / PNG でダウンロード（印刷用に余白・「アンケートにご協力ください」の定型文つき）。**スタッフ名をラベルにしない旨の注意書き**（§2）。
- **低評価の基準**: 評価スケールの閾値（既定: 1〜2 を「低評価」、3 を「要確認」）。
- **通知**: v1 は管理画面内（サイドバーのバッジ + 未対応の件数）。メール通知は送信サービスが無いので後回し（§9 #4）。

### 4.2 閲覧・分析

- **回答一覧**: 時系列。列 = 日時、経路（QR ラベル）、評価、自由記述の冒頭、直接連絡の有無、投稿ボタンの押下、対応状態（未対応 / 対応中 / 対応済み）、対応メモ。**並び替え**: 日時 / 評価 / 対応状態（低評価・直接連絡を上に）。**絞り込み**: 期間・経路・評価・対応状態。
- **低評価の一覧**: 上の一覧を「低評価 or 直接連絡あり」で絞った既定ビュー。対応メモと対応済みの記録（誰が・いつ）。
- **指標**（すべて近似であることを画面に明記）:
  - 回答数、評価の平均と分布、経路別・期間別の推移。
  - **投稿ボタン押下数と押下率**。「Google 側で実際に投稿されたかは取得できません」を固定表示。
  - **口コミ件数の推移**（週次の MEO 報告書 `meo_reports` の `ratingCount` から）。押下数と並べて「導入前後の増え方」を見せられる。これは既存機能の流用で費用ゼロ。
- **エクスポート**: CSV（回答・対応メモ）。

## 5. 差別化のポイント（たたき台のまま）

「口コミにならなかった不満が店舗にだけ届く」を主価値に据える。低評価の人は投稿しないので、その声を店舗が最初に受け取り改善に使える。ゲーティングをせずに、店舗の「悪い口コミを減らしたい」という本音に応える。**説明資料では「悪い口コミを消す・隠す」ではなく「悪い口コミになる前に直せる」と言い切る。**

## 6. 業種別のアンケート テンプレート（案）

質問は体験を思い出す順に並べる。店名・メニュー名・スタッフ名は入れない（店舗が自分で足すのは可だが、口コミへの誘導目的は不可と注意書き）。

**飲食**
1. 今日のご来店の満足度は？（1〜5）
2. 特に良かったのは？（複数選択: 味 / 量 / 価格 / 提供の速さ / 接客 / 店内の雰囲気 / 清潔さ）
3. 良かった点があれば教えてください（自由記述）
4. 気になった点・改善してほしい点があれば教えてください（自由記述）
5. どなたとご来店？（単一: ひとり / 家族 / 友人 / 仕事）

**サロン（美容室・ネイル・エステ）**
1. 本日の仕上がりの満足度は？（1〜5）
2. 良かったのは？（複数選択: 仕上がり / カウンセリング / 施術中の説明 / 待ち時間 / 店内の雰囲気 / 料金）
3. 仕上がりや施術で良かった点（自由記述）
4. 気になった点・次回に向けての要望（自由記述）
5. 次回も利用したいですか？（単一: ぜひ / たぶん / わからない / いいえ）

**クリニック（§2 の確認が済むまで保留）**
- 提供する場合も、症状・治療効果に触れる質問は置かない（待ち時間・説明のわかりやすさ・受付の対応・院内の清潔さ・予約の取りやすさ に限る）。

## 7. 守るべき線引き（ツールの設計思想。店舗向け説明資料にも載せる）

1. 評価による投稿導線の出し分けはしない。
2. 店舗が投稿文を用意・固定・強制する機能は作らない（AI 下書きも含む）。
3. 口コミ投稿への特典付与は機能として提供しない。
4. 口コミに含める語（店名・メニュー・スタッフ名）の指定は依頼しない。
5. スタッフごとの口コミ目標は置かない（QR のスタッフ別発行を推奨しない）。
6. 回答者と Google の投稿者を突き合わせない。
7. 「なぜやらないか」= Google の削除・警告と過去口コミの一括削除、景表法の措置命令（事業者名の公表）を、店舗向け資料に事例つきで書き、追加要望を断る根拠にする。

## 8. 既存アプリへの組み込み（技術設計）

### 8.1 位置づけ

| 項目 | 値 |

### 8.2 テーブル（Supabase SQL Editor で実行。実装時に OPERATIONS.md の「フェーズ 2 で使うテーブル」へ転記）

```sql
create table if not exists review_forms (
  id uuid primary key default gen_random_uuid(),
  user_id text not null,
  place_id text not null,
  slug text not null unique,            -- 12 文字の URL 用ランダム文字列
  title text not null,
  questions jsonb not null,             -- ReviewQuestionSchema[]（最大 8）
  low_rating_max int not null default 2,
  write_review_url text,                -- Places の writeAReviewUri（無ければ place_id から組み立て）
  active boolean not null default true,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create index if not exists review_forms_user_idx on review_forms (user_id, place_id);

create table if not exists review_channels (   -- QR の発行単位
  id uuid primary key default gen_random_uuid(),
  form_id uuid not null references review_forms (id) on delete cascade,
  code text not null,                    -- QR に埋める ?c=xxxx（6 文字）
  label text not null,                   -- 店舗 / テーブル 3 / レジ …
  created_at timestamptz not null default now(),
  unique (form_id, code)
);

create table if not exists review_responses (
  id uuid primary key default gen_random_uuid(),
  form_id uuid not null references review_forms (id) on delete cascade,
  channel_id uuid references review_channels (id) on delete set null,
  rating int,                            -- 評価スケールの答え（1〜5）
  answers jsonb not null,                -- { questionId: value }
  is_low boolean not null default false, -- rating <= low_rating_max
  direct_message text,                   -- 「お店に直接伝える」の本文
  direct_contact text,                   -- 任意の連絡先（暗号化はしない。保持期間は §8.4）
  clicked_review_at timestamptz,         -- Google ボタン押下
  clicked_direct_at timestamptz,
  status text not null default 'open',   -- open / in_progress / done
  note text,                             -- 店舗の対応メモ
  handled_at timestamptz,
  created_at timestamptz not null default now()
);
create index if not exists review_responses_form_idx on review_responses (form_id, created_at desc);
create index if not exists review_responses_low_idx  on review_responses (form_id, is_low, status);

alter table review_forms     enable row level security;
alter table review_channels  enable row level security;
alter table review_responses enable row level security;
```

`user_id` の絞り込みはサーバーが必ず付ける（`history.ts` と同じ作法。`review_responses` は `form_id` 経由で `review_forms.user_id` を確認）。公開 API は `slug` と `active` でしか行を引けない。

### 8.3 QR コードの生成

依存を増やさない方針だが、QR の符号化を自前で書くのは割に合わない。**`qrcode`（npm、MIT）を 1 つ追加**し、サーバー側で SVG を生成して返す（ブラウザには渡さない）。代替: 依存ゼロで済ませるなら `/r/<slug>` の URL だけ返し、店舗が任意の QR 生成サービスで作る（v1 の最小構成として可）。

### 8.4 個人情報・規約

- アンケートは既定で氏名・連絡先を集めない。「お店に直接伝える」の連絡先は任意。
- 来店客は当サービスの利用者ではないので、`/r/<slug>` の下部に**「この画面は SEO 研究所が提供し、回答は店舗に届きます」と `/privacy` へのリンク**を置く。`/privacy` に「店舗のアンケート回答（第三者提供先 = その店舗、保持期間）」の条を追加。**利用規約に、店舗側の禁止事項（§7 の 1〜6）を追加**する。
- 保持期間: 回答は店舗が削除するまで。連絡先は 90 日で自動的に空にする（Cron）。
- 回答の `answers` は第三者由来の文字列。表示は React のエスケープに任せ、CSV は式インジェクション対策（先頭の `=`, `+`, `-`, `@` を無効化）。
