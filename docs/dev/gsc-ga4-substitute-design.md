# GSC / GA4 を連携なしで代替する（設計メモ）

**利用者の決定 2026-09-17**:
> CS が大変ですし、そこにコストを掛けられないので、**API の料金が上がってでも何としても GA4 と GSC の機能を模倣したい**。

判断の軸が決まった: **API 費用 < CS 費用**。連携の説明・代行に人の時間を使うくらいなら、金を払って自動で取る。

## 結論（先に）

| 対象 | 代替できるか | 方法 | 規模 |
|---|---|---|---|
| **GSC** | **ほぼ代替できる** | DataForSEO Labs でドメインの獲得キーワードを自動発見 → 順位 × 検索数 × CTR で推定 | 2〜3 日 |
| **GA4（流入の量と経路）** | **推定できる** | 同上の集計。オーガニックのみ | 上に含む |
| **GA4（サイト内の行動・CV）** | **外部からは不可能** | **自前の計測タグを配る**しかない | 5〜7 日 |

**GA4 の「サイト内で何が起きたか」は、どの外部 API でも取れない。**
Similarweb 等の推定サービスはあるが、**日本の中小・店舗サイトの規模では数字が出ない**（推定に必要な母数が足りない）。
ここを埋める唯一の手は、**GA4 の代わりに自前の 1 行タグを配ること**。GA4 の設定を説明する CS がまるごと消える。

## 第 1 段: GSC の代替（2〜3 日）

### いまある部品

| 部品 | 場所 | 状態 |
|---|---|---|
| 順位の取得 | `src/lib/serp/`（SerpApi） | **稼働中** |
| 順位別 CTR カーブ | `src/lib/site-report/findability.ts` の `ctrForRank` | **実装済み** |
| 月間検索数の保存 | `src/lib/rank/store.ts` の `monthlyVolume` | **あるが手入力** |
| DataForSEO の呼び出し | `src/lib/geo/dataforseo.ts` | **稼働中**（SERP と LLM 用） |

### 足すもの

1. **ドメインの獲得キーワードの自動発見**（ここが肝）
   DataForSEO Labs の「ranked keywords」系エンドポイントに**ドメインを渡すと、そのドメインが順位を持っているキーワードの一覧**が、
   検索数・順位・推定流入つきで返る。**これが GSC のクエリ一覧に最も近い代替物。**
   - お客様のキーワード登録作業が**不要になる**（いまは手入力）。CS が減る。
   - 月 1 回でよい。**1 ドメインあたり 1 リクエスト。**
   - **要確認: 正確なエンドポイント名と単価**（この開発環境から dataforseo.com のドキュメントに接続できないため、
     実装前に利用者の画面かこちらの疎通確認で確定する）。
2. **月間検索数の自動取得**（手入力の `monthlyVolume` を埋める）
3. **推定値の計算**（既存の関数を使うだけ）
   - 推定表示回数 ≒ 月間検索数
   - 推定クリック数 ≒ 月間検索数 × `ctrForRank(順位)`
   - 推定 CTR = 上の 2 つの比
4. **画面**: 「検索パフォーマンス（推定）」。GSC を連携していれば**実測に自動で切り替える**。

### 代替できないもの（画面に明記する）

- **実際の検索クエリ**（Google が「このクエリで表示された」と言っている一次データ）
- インデックス状況・カバレッジのエラー
- 表示回数の実数（推定は「検索数 = 表示回数」と置いているので、実際とはずれる）

**「推定」と「実測」をラベルで必ず区別する。**混ぜると信用を失う。

## 第 2 段: GA4 の代替 = 自前の計測タグ（5〜7 日）

### なぜ外部 API では無理か

GA4 が持っているのは**サイトの中で起きたこと**（セッション、回遊、滞在、フォーム送信、電話クリック）。
これはサイト上でスクリプトが動いていないと観測できない。**外から推定する方法は原理的に無い。**
Similarweb 等の推定は大規模サイト向けで、**月数百セッションの店舗サイトでは値が出ないか、誤差が大きすぎる。**

### 自前タグなら何が変わるか

| | GA4 を使う場合 | 自前タグ |
|---|---|---|
| お客様の作業 | Google アカウント → GA4 プロパティ作成 → データストリーム → タグ設置 → イベント設定 → 権限付与 | **発行した 1 行を貼るだけ** |
| CS の説明量 | 大きい（画面が多く、用語も多い） | **1 行** |
| イベント名の揺れ | 会社ごとにバラバラ（いまの「GA4 イベントの割り当て」画面はこの揺れを吸収するための機能） | **こちらが定義するので揺れない** |
| データの持ち主 | Google | **こちら（Supabase）** |
| 過去データ | 設置日より前は取れない | 同じ（ただし設置が簡単なので早く始まる） |

**「GA4 イベントの割り当て」という画面が存在すること自体が、GA4 を使う限り避けられない複雑さの証拠。**自前タグならこの画面ごと不要になる。

### 作るもの

| # | 中身 | 備考 |
|---|---|---|
| 1 | **タグの配信** `GET /t.js?s=<サイトID>` | 数 KB。非同期。お客様は `<script async src=...>` を 1 行貼るだけ |
| 2 | **収集エンドポイント** `POST /api/t` | ページビュー、参照元、UTM、滞在、スクロール、クリック（電話・メール・外部予約）、フォーム送信 |
| 3 | **保存** Supabase | 生ログは短期（例 90 日）、日次集計は長期。行数が費用に効くので集計を先に作る |
| 4 | **同意とプライバシー** | Cookie を使わず、**IP は保存せず**、端末識別子は日次で使い捨てにする設計にすれば、同意バナー不要の範囲に収めやすい。**要・専門家確認**（#12 と同じ枠） |
| 5 | **画面** | いまの「サイトレポート」「生成 AI 流入分析」を、GA4 ではなく自前データで描き直す（#96 の経路問題もこれで消える） |
| 6 | **生成 AI 流入の判定** | 参照元のホスト名で判定する。`src/lib/ga4/ai-sources.ts` の辞書を**そのまま流用できる** |

### 費用

- Vercel の関数呼び出しと Supabase の行数。**月数百〜数千セッションの店舗サイトなら微々たるもの。**
- **GA4 の代わりなので、GA4 側の API 費用はゼロになる。**

### 段階

1. **最小構成**（3 日）: ページビュー + 参照元 + 主要クリック 3 種（電話・メール・外部予約）。日次集計。
2. **CV まわり**（2 日）: フォーム送信の検知、完了ページの指定。
3. **画面の差し替え**（2 日）: サイトレポートと生成 AI 流入分析を自前データに。
