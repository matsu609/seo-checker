## 0. 目的と前提

### 0.1 目的
ChatGPT / Gemini / Google AI Overviews（AIO）等のAI検索において、顧客ブランドがどの程度「引用」「参照」されているかを定期計測し、競合と比較可能なダッシュボードとして提供するSaaS。

### 0.2 最重要制約
- **1アカウント（1社）あたりのシステム原価を月¥3,000以内**に収める
- 内訳目安: インフラ按分 ¥800 / 変動費（計測・生成）¥2,200
- 為替前提: 1USD = ¥160（設定値として外出しし、変更可能にする）
- 変動費の1割はバッファ（リトライ・障害時再実行・為替変動）として予約

### 0.3 設計思想（優先順位）
1. 原価は「計測回数」ではなく「生成処理」と「Liveモード」で膨らむ。絞る対象を間違えない
2. 統計的に言えないことをUIで言わない。集計レベルで語り、個別プロンプトの週次比較を主指標にしない
3. 人件費（CS問い合わせ）はAPI費より圧倒的に高い。数十円で問い合わせが減るなら投資する

## 1. データ取得層

### 1.1 データソースと単価（DataForSEO準拠、設計上の基準値）

| データ種別 | エンドポイント | 単価 | 備考 |
|---|---|---|---|
| 検索順位 | SERP Advanced | $0.002 / KW | |
| AIO取得 | SERP Advanced + `load_async_ai_overview` | $0.0026 / KW | AIO参照リンクは構造化データで返る |
| LLM計測（ChatGPT / Gemini） | LLM Scraper 標準キュー | $0.0012 / 回 | **定期実行はこれ固定** |
| LLM計測（優先） | LLM Scraper 優先キュー | $0.0024 / 回 | 使用しない |
| LLM計測（リアルタイム） | LLM Scraper Live | $0.004 / 回 | 手動オンデマンド実行のみ許可 |
| その他LLM（Claude / Perplexity等） | LLM Responses | 各社API従量 | 上位プランで追加 |

- 単価はすべて設定テーブルで管理し、コード内にハードコードしない
- プロバイダは抽象化（`DataProvider` インターフェース）し、将来の自社スクレイピング切替に備える

### 1.2 実行モードのルール
- **定期バッチは必ず標準キュー**（ターンアラウンド最大45分）。ユーザーは翌日に結果を見るため待ち時間は体感されない
- Liveモードはユーザーが明示的に「今すぐ実行」を押した場合のみ。クレジット消費を重くする（§6）

### 1.3 Gemini引用URLの解決
- Geminiはリダイレクト形式（vertexaisearch経由）で返ることがある
- 最終ドメインまで解決する処理を実装（自前HTTP HEAD/GET、キャッシュあり）
- 解決失敗時は `unresolved` としてログし、引用判定からは除外せず「不明ドメイン」として保持

## 2. 計測設計

### 2.1 標準プラン（単一サイト）の計測構成

| 項目 | 構成 | 月間計測数 | 月額原価 |
|---|---|---|---|
| 検索順位 | 200KW × 週1 | 800 | $1.60 |
| AIO取得 | 50KW × 週1 | 200 | $0.52 |
| LLM計測（通常プロンプト） | 30プロンプト × 3モデル × 3回 × 週1 | 1,080 | $1.30 |
| LLM計測（高精度プロンプト） | 5プロンプト × 3モデル × 追加7回 × 週1 | 420 | $0.50 |
| 言及抽出・分類 | 軽量モデル、全レスポンス | — | 約$1.0 |
| 週次レポート生成 | 軽量モデル × 4回 | — | $1.50 |
| 月次深掘り分析 | 高性能モデル × 1回 | — | $2.00 |
| インフラ按分 | | | $5.00 |
| **合計** | | | **約$13.4 ≒ ¥2,150** |

→ ¥3,000枠に対して約¥850の余裕。この余裕はユーザーのオンデマンド実行枠に充てる。

### 2.2 反復回数（n）の設計
- **通常プロンプト: n=3 / 週**
- **高精度プロンプト: n=10 / 週**（ユーザーが3〜5本を指定）
- 指名検索（ブランド名を含むプロンプト）は回答がほぼ決定論的なため **n=3固定**。高精度枠は非指名（一般語・比較系）プロンプトに温存する。UI上で指名プロンプトを高精度指定しようとした場合は警告を出す

### 2.3 日次分散（必須）
- 反復は**同一バッチで連続実行しない**。週内の異なる日に分散させる
  - n=3: 月・水・金に1回ずつ
  - n=10: 月〜金に2回ずつ
- 理由: 連続実行はデコーディングのランダム性しか捉えない。モデル更新・インデックス更新・時間帯差を捉えるには時間分散が必要
- 実装: 週次バッチではなく日次バッチとし、各プロンプトに「今日実行すべき回数」を持たせる

### 2.4 実行日の顧客間分散
- 全顧客を同一曜日・同一時刻に走らせない。契約ごとに開始曜日オフセットを割り当ててピークを平準化する
- 目的: スクレイピングのブロック率低減、インフラの山の抑制（原価自体は変わらない）

## 3. 指標定義

### 3.1 引用と参照（同一レスポンスから抽出、追加API費用なし）

| 指標 | 定義 | 取得元 |
|---|---|---|
| **引用 (citation)** | 回答のソース欄・インラインリンクに対象ドメインが含まれる | citations / references 配列 |
| **参照 (mention)** | 回答本文にブランド名（エイリアス含む）が出現。リンク有無は問わない | 本文テキスト |

- 引用は「自社」「競合」「第三者」の3分類でドメインを判定する（§4）
- 1レスポンスにつき、自社・各競合について {引用: bool, 参照: bool, 出現順位: int|null, 引用ドメイン一覧} を記録

### 3.2 指名検索プロンプトの主指標
参照率は天井に張り付く（95〜100%）ため主指標にしない。以下を主指標とする。

- **自社引用率**: 指名プロンプトのうち自社ドメインが引用された割合
- **引用元構成比**: 自社 / 第三者メディア / 競合 の内訳
- **競合同時言及率**: 指名プロンプトの回答に競合ブランドが参照された割合

### 3.3 非指名プロンプトの主指標
- **ブランドシェアスコア**: 対象プロンプト群の全観測に対する自社参照率（競合も同様に算出）
- **引用シェア**: 同じく引用ベース
- 見出し数値は **4週ローリング**（通常プロンプトでn=12、高精度でn=40）

### 3.4 集計単位
- 最小粒度: プロンプト × モデル × 実行日時 × 反復番号
- 表示粒度: プロンプト群（全体 / タグ別）× モデル × 週 / 4週ローリング

## 4. ブランド正規化

### 4.1 エイリアス登録（オンボーディング必須）
- 自社および各競合について、以下をエイリアスとして登録する
  - 正式名称、カナ表記、英字表記、略称、サービス名／製品名
- エイリアスはユーザーが編集可能。変更履歴を保持

### 4.2 参照判定
- 単純文字列マッチではなく、**軽量LLMによる文脈判定**を行う（同名の一般名詞・他社との誤検出を防ぐ）
- 判定結果には confidence を持たせ、低confidenceは「要確認」フラグでUIに出す（自動で除外しない）

### 4.3 ドメイン分類
- 自社ドメイン: オンボーディングで登録（サブドメイン含む）
- 競合ドメイン: 競合ごとに登録
- 上記以外: 第三者。可能であれば「比較サイト / 口コミ / ニュース / その他」を自動分類（軽量LLM）

## 5. 統計・表示ルール

### 5.1 UIで守ること
1. **見出し数値は4週ローリング**。週次の生の数値は詳細ビューのみ
2. **信頼区間をバンド表示**する（Wilson区間）。折れ線は幅を持たせる
3. **細かい差を丸める**。通常プロンプト（n=12）のプロンプト単体表示は「よく言及される / たまに / ほぼ無し」等の3〜4段階
4. 高精度プロンプト（n=40）はパーセント表示を許可（CI ±15pt程度）
5. 「有意差あり」の文言はUIで使わない。「大きな変化を検出」等、精度に見合った表現にする

### 5.2 精度の期待値（実装者向けメモ）
- n=3 vs 3: 完全分離（0/3→3/3）でもFisher両側p=0.10。単独では何も言えない
- n=10 vs 10: 40〜50pt規模の変化は検出可（検出力55〜75%）。20ptは不可
- n=40（4週ローリング）: 95%CI ±15pt
- 集計（30プロンプト×3モデル×3回×4週=1,080観測、実効n≈300）: 全体シェア標準誤差≈3%、10pt規模の変動は検出可

### 5.3 モデルバージョンログ（必須）
- 全計測にモデルバージョン（取得可能な範囲で）と取得日時を記録
- バージョン変化を検知したら、グラフ上に**更新日マーカー**を自動描画
- 理由: モデル更新による階段状の変化はサンプル数で平滑化できない。問い合わせの大半はこれで説明可能

## 6. クレジット制

### 6.1 基本設計
- **1クレジット = 原価¥1相当**
- 標準プラン: **月2,000クレジット付与**
- **繰越なし、月次リセット**（未使用分を負債にしない）
- 上限到達時はソフトキャップ: 定期実行は継続し、オンデマンド実行のみ停止。超過課金は初期は行わない（将来オプション）

### 6.2 消費レート

| アクション | 消費クレジット | 実原価目安 |
|---|---|---|
| 順位・AIO計測（1KW） | 0.5 | ¥0.32〜0.42 |
| LLM計測 標準キュー（1プロンプト×1モデル×1回） | 0.5 | ¥0.19 |
| LLM計測 Liveモード（同上） | 2 | ¥0.64 |
| 週次レポート生成 | 30 | |
| 月次深掘り分析・ファンアウト抽出 | 150 | |

### 6.3 標準構成での消費見込み
- 順位・AIO: 1,000計測 × 0.5 = 500
- LLM通常: 1,080 × 0.5 = 540
- LLM高精度: 420 × 0.5 = 210
- 週次レポート: 30 × 4 = 120
- 月次深掘り: 150
- **合計 約1,520 / 2,000** → 残480がオンデマンド枠

### 6.4 高精度プロンプト枠
- 標準プラン: 3〜5本（ユーザー指定トグル）
- 変更は月1回まで。変更時はグラフに「高精度モード開始」マーカー
- 拡張オプション: 10本（追加原価 約¥175/月、販売価格は別途）

## 7. 原価最適化（実装必須）

### 7.1 計測結果の顧客間共有（最重要）
- KW・プロンプトを正規化（全角半角・空白・大文字小文字・句読点）してハッシュ化
- 同一ハッシュ × 同一モデル × 同一ロケール の結果は **24時間以内ならキャッシュから返す**
- 顧客ごとの抽出（自社／競合の判定）はキャッシュされた生レスポンスに対して個別に実行
- 効果: 同業顧客が増えるほど1社あたり原価が下がる。実効原価¥1,000台を目標

### 7.2 生成処理の二層化
- 週次レポート: 軽量モデル + テンプレート埋め込み
- 月次深掘り: 高性能モデル、月1回のみ
- 生成コストは計測コストの数倍になりやすい。絞る対象はここ

### 7.3 差分実行
- AIO・LLM回答が前回とほぼ同一（類似度閾値以上）のKW/プロンプトは、要約・分析の再生成をスキップ
- スクレイピングは実行するが生成は走らせない
- 週次変化率は2〜3割程度の想定。生成費を約7割削減

### 7.4 標準キュー固定
- 定期実行でLive/優先キューを呼ぶコードパスを設けない（設定でも切り替えられないようにする）

## 9. バッチ処理フロー

1. 日次スケジューラ（顧客ごとの `run_day_offset` を考慮）
2. 当日実行対象の Keyword / Prompt を抽出。反復回数は §2.3 の分散ルールに従い当日分のみ
3. 正規化ハッシュでキャッシュ照会。24h以内のヒットがあれば再利用、なければ標準キューに投入
4. 結果取得 → Gemini URL解決 → raw保存
5. アカウントごとに Observation 生成（エイリアス判定・ドメイン分類、軽量LLM）
6. 差分判定 → 変化ありのもののみ要約生成対象に
7. Aggregate 更新（週次・4週ローリング、Wilson CI）
8. モデルバージョン変化検知 → ModelVersionEvent
9. CreditLedger 記帳（キャッシュヒット分も記帳するかは要決定 → §11）
