## 1. 目的

Google Search Console、Google Analytics 4、必要に応じて CRM データを取り込み、Web サイトの状態を自動診断する。

数値集計とパターン判定は通常のプログラムで行い、LLM は確定した数値と診断結果をもとに、顧客向けの説明、原因候補、確認質問、改善施策を生成する。

本システムはコンサルタントの判断を完全に置き換えるものではなく、以下を目的とする。

- 分析作業の標準化
- 集計ミスの防止
- 担当者による回答品質の差を削減
- コンサル資料作成時間の短縮
- 顧客ごとの説明文の自動生成
- 改善施策の優先順位付け
- 分析根拠と推測の明確な区別

## 2. 結論

推奨構成は「ルール判定 + LLM」のハイブリッド方式とする。

```
データ取込
  ↓
データ検証・正規化
  ↓
プログラムによる数値集計
  ↓
診断ルールによるパターン判定
  ↓
重要度・確度・影響度の評価
  ↓
LLM による説明文生成
  ↓
人間による確認
  ↓
顧客への提示
```

以下は LLM へ任せない。

- CSV の数値集計
- 増減率の計算
- CTR や CVR の計算
- 比較期間の分割
- 指名検索の分類
- URL 候補の抽出
- 高表示・低クリックなどの一次判定
- 診断ルールの発火判定
- 最低データ量の確認

以下を LLM へ任せる。

- 経営者向けの説明
- Web 担当者向けの詳細説明
- 複数ルールの統合
- 原因候補の整理
- 顧客への確認質問
- 優先施策の文章化
- 30 日・90 日の改善計画
- 業界に応じた表現
- 多言語化
- 顧客からの追加質問への回答

## 3. 分析レイヤー

分析は上流から下流へ、5 つのレイヤーに分ける。

```
レイヤー1：検索需要・検索露出
GSC：表示回数、掲載順位、クエリ
        ↓
レイヤー2：検索結果からの流入
GSC：クリック、CTR、ページ、デバイス、国
        ↓
レイヤー3：サイト到着後の閲覧
GA4：セッション、ランディングページ、エンゲージメント
        ↓
レイヤー4：問い合わせ行動
GA4：CTA クリック、フォーム開始、フォーム完了、キーイベント
        ↓
レイヤー5：商談・受注
CRM：有効リード、商談化、見積、受注、売上
```

原因は原則として上流から順番に確認する。

```
表示されていない
→ インデックス、検索需要、コンテンツの問題

表示されるがクリックされない
→ 順位、タイトル、検索意図の問題

クリックされるが GA4 セッションにならない
→ 計測、URL、同意設定、流入元分類の問題

訪問されるが読まれない
→ 内容、表示速度、検索意図、デバイス表示の問題

読まれるが CTA を押されない
→ 訴求、事例、価格、導線の問題

CTA を押すがフォームを開始しない
→ 遷移先、オファー、心理的負担の問題

フォームを開始するが完了しない
→ 項目数、入力エラー、操作性の問題

問い合わせるが商談にならない
→ ターゲット顧客、訴求、条件の問題

商談になるが受注しない
→ 価格、仕様、提案、営業プロセスの問題
```

会社によって GA4 のイベント名が異なるため、システム内部では共通イベントへ変換する。

      - inquiry_button
      - request_quote
      - demo_request

  form_start:
    description: "問い合わせフォームの入力開始"
    examples:
      - form_start
      - contact_form_start
      - inquiry_start

  form_complete:
    description: "問い合わせフォームの正常完了"
    examples:
      - generate_lead

      - contact_complete
      - inquiry_complete

  document_download:
    description: "カタログや仕様書のダウンロード"
    examples:
      - file_download

## 6. URL の正規化

GSC と GA4 では URL 表記が異なる場合があるため、比較前に正規化する。

**正規化する項目**

- http と https
- www の有無
- ドメインの大文字・小文字
- URL 末尾の不要なパラメータ
- URL フラグメント
- UTM パラメータ
- 末尾スラッシュ

**自動統合しない項目**（別ページである可能性があるため、確認なしに統合しない）

- `.html` の有無
- 日本語・英語・中国語の URL
- `/ja/`、`/en/`、`/zh/`
- 商品 ID や記事 ID
- ページネーション
- カテゴリーと個別ページ
- PDF と HTML ページ

URL が似ているだけでは、重複コンテンツやカニバリゼーションと断定しない。

## 7. 基本計算

**増減率**

```
増減率 =（当期値 - 前期値）÷ 前期値
```

前期が 0 の場合は増減率を計算せず、「新規発生」とする。

**CTR**

```
CTR = クリック数 ÷ 表示回数
```

CSV に含まれる行別 CTR の単純平均は使用しない。

**エンゲージメント率**

```
エンゲージメント率 = エンゲージのあったセッション ÷ 全セッション
```

**CTA クリック率**

```
CTA クリック率 = CTA クリックが発生したセッション ÷ 対象ページのセッション
```

**フォーム開始率**

```
フォーム開始率 = フォーム開始セッション ÷ CTA クリックセッション
```

**フォーム完了率**

```
フォーム完了率 = フォーム完了セッション ÷ フォーム開始セッション
```

**Organic CVR**

```
Organic CVR = Organic Search 経由のフォーム完了セッション ÷ Organic Search セッション
```

**クエリ取得率**

```
クエリ取得率 = クエリ CSV のクリック合計 ÷ GSC サイト全体のクリック数
```

クエリ取得率が低い場合、指名検索比率や非指名検索比率をサイト全体の正確な比率として扱わない。

**指名検索比率**

```
指名検索比率 = 指名検索クエリのクリック数 ÷ クエリ CSV のクリック合計
```

必ず「CSV に表示されたクエリ内での比率」と表現する。

## 8. 初期判定の共通閾値

閾値は管理画面から変更できる設計とする。

```yaml
default_thresholds:

  minimum_analysis_days: 28
  minimum_total_impressions: 500
  minimum_rule_impressions: 100
  minimum_sessions: 100

  major_increase_rate: 0.20
  major_decrease_rate: -0.20
  flat_change_range: 0.05

  significant_position_change: 2.0
  high_brand_click_share: 0.60
  low_query_coverage: 0.70

  low_ctr_top3: 0.03
  low_ctr_top10: 0.01

  device_ctr_gap_rate: 0.40
  low_engagement_rate: 0.40
  low_form_completion_rate: 0.30

  abnormal_daily_multiplier: 3.0
  high_homepage_click_share: 0.60
  high_foreign_impression_share: 0.20
```

これらは絶対的な良否基準ではなく、一次判定用の初期値とする。
BtoB、BtoC、EC、採用、メディアでは適正値が異なる。

## 9. 診断ルール

### 9.1 データ品質ルール

| ID | パターン | 判定内容 |
|---|---|---|
| D01 | 分析期間不足 | 分析期間が 28 日未満 |
| D02 | 比較期間不一致 | 前期と当期の日数が異なる |
| D03 | データ量不足 | 表示回数またはセッション数が最低値未満 |
| D04 | クエリ取得率不足 | クエリクリック合計が全体クリックの 70% 未満 |
| D05 | 必須ファイル不足 | クエリ、ページ、日付などが不足 |
| D06 | ファイル名と内容の不一致 | ファイル名と列名が一致しない |
| D07 | 欠損値 | 数値列に空欄や不正値がある |
| D08 | 異常値 | 日別値が中央値の 3 倍以上 |
| D09 | タイムゾーン不一致 | GSC と GA4 の日付区切りが異なる |
| D10 | 集計単位不一致 | サイト、ページ、ユーザー、セッションを混同 |
| D11 | イベント設定変更 | 比較期間中にイベント定義が変わった |
| D12 | タグ未設置ページ | 一部ページで GA4 が計測されていない |
| D13 | 社内アクセス混入 | 社員や制作会社のアクセスが多い |
| D14 | ボット・スパム疑い | 不自然な国・参照元・行動が集中 |
| D15 | 期間中のサイト移行 | URL やドメイン変更が比較へ影響 |

## 10. GA4 診断ルール

### 10.1 集客ルール

| ID | パターン | 主な判断 |

## 15. 重要度と確度

**重要度**

- **Critical**: 計測不能、サイト障害、重大なインデックス問題
- **High**: 問い合わせや主要ページへ直接影響する
- **Medium**: 改善効果は見込めるが緊急性は低い
- **Low**: データ量が少ない、影響範囲が限定的

**確度**

- **High**: データから直接確認できる
- **Medium**: 複数の数値が同じ可能性を示す
- **Low**: 追加データがないと判断できない

**優先度スコア例**

```
優先度スコア = 重要度 × 影響量 × 確度 ÷ 実装負担
```

```yaml
score_mapping:
  severity:
    critical: 4
    high: 3
    medium: 2
    low: 1

  confidence:
    high: 1.0
    medium: 0.7
    low: 0.4

  implementation_effort:
    small: 1
    medium: 2
    large: 3
```

顧客向けの優先施策は、原則として上位 3 件に絞る。

## 18. 誤判定防止ルール

以下をシステム全体の禁止事項とする。

- クエリ CSV の合計をサイト全体の合計とみなさない
- ページ CSV の表示回数合計をサイト全体と単純比較しない
- 平均掲載順位を検索順位の固定値として扱わない
- 表示回数が少ない CTR を重大問題として扱わない
- 指名検索比率を、クエリ取得率を無視して断定しない
- モバイル CTR が低いだけでレスポンシブ表示の問題と断定しない
- 海外表示が多いだけで海外需要があると断定しない
- 検索での見え方が空欄でも構造化データエラーと断定しない
- URL が複数あるだけで重複コンテンツと断定しない
- 滞在時間が長いだけで良いページと断定しない
- 直帰率が高いだけで悪いページと断定しない
- イベント数を問い合わせ人数として扱わない
- キーイベントを受注として扱わない
- Organic セッション増加を SEO の成果と即断しない
- GSC クリック数と GA4 セッション数の完全一致を求めない
- 前年同期がない状態で季節性を断定しない
- サイト更新と数値変化の相関だけで因果関係を断定しない
- LLM に存在しない数値を補完させない
- LLM に最終的な計算を任せない

## 23. テスト項目

**数値テスト**

- CTR がクリック ÷ 表示回数になっている
- CVR が完了セッション ÷ 対象セッションになっている
- 前期 0 の場合にゼロ除算しない
- 比較期間の日数を確認している
- パーセント文字列を正しく数値化している
- GSC と GA4 のタイムゾーンを確認している

**診断テスト**

- 表示増・クリック横ばいで T02 が発火する
- 指名検索比率が高い場合に Q01 が発火する
- クエリ取得率が低い場合に D04 も発火する
- モバイル CTR が低くても、UX 問題と断定しない
- URL 形式が複数でも重複と断定しない
- GA4 がない場合、訪問後の問題を断定しない
- CRM がない場合、受注貢献を断定しない

**LLM テスト**

- 入力にない数字を生成しない
- 事実と推測を分離する
- 優先施策を 3 件以内にする
- 根拠数値を表示する
- 不足データを明記する
- 同じ内容を繰り返さない
- 業界に合わない施策を出さない
- 「必ず改善する」などの保証表現を使わない

## 24. 成功指標

システム自体の評価指標は以下とする。

- 1 社あたりの分析時間
- コンサル資料作成時間
- 数値集計の正答率
- 診断ルールの再現率
- 人間による修正率
- 根拠のない断定の発生件数
- 顧客からの追加質問数
- 提案施策の実行率
- レポート継続利用率
- 商談化率

目標例:

| 指標 | 目標 |
|---|---|
| 分析時間 | 従来の 50% 以上削減 |
| 数値集計正答率 | 100% |
| 重大な根拠不明断定 | 0 件 |
| 優先施策の人間修正率 | 20% 以下 |

## 25. 最終方針

本システムでは、考えられる複合パターンをすべて事前登録しない。代わりに、以下の構成とする。

```
約100～150個の独立した診断ルール
＋
重要度・確度・影響度の評価
＋
LLMによる複数ルールの統合
＋
人間による最終確認
```

これにより、GSC、GA4、CRM を組み合わせても、パターン数の爆発を防げる。
最も重要な設計原則は以下である。

```
計算はプログラム
診断はルール
説明はLLM
承認は人間
```

この分担によって、再現性、説明力、拡張性、安全性を両立する。

| | 精密診断（r56〜r60、実装済み） | この仕様書の診断（新規） |

3. **何をどう数えたかを必ず開示する**。報告書の「訪問後の流れ」の下と事実シートに、
   共通イベントごとの実際のイベント名を出す。割り当てが無い段階は 0 ではなく「未計測」と表示する。

- ルール本体は**宣言（データ）とエンジン（純関数）に分ける**。1 ルール = 1 オブジェクトなので、ルールを足すのにコードは増えない。

- **再現性**（§20）のため、`RULES_VERSION` / `THRESHOLDS_VERSION` / `PROMPT_VERSION` を定数に置き、`analysis_runs` に保存する。

### 27.2 報告書の見せ方（2026-09-16）

134 ルールあるので、発火したものを全部そのまま並べると読めない。§15 の
「顧客向けの優先施策は原則として上位 3 件に絞る」に合わせ、`summary.ts`（純関数）で
読む順番を組み立てる。

1. **まず手を付けるところ**（優先度の上位 3 件）— 何が起きているか 1 行 + 最初の一歩
2. **訪問したあと、どこで止まっているか**（ファネル）— いちばん落ちている段階を名指しする
3. **そのほかに見つかったこと** — 重大・高は開き、中・低は折りたたむ
4. **つなぐと分かること** — 判定していない範囲を、利用者の行動に翻訳する

決めごと:

- **ルール ID（T02 など）は内部の符号**なので、行の先頭に置かない。詳細を開いたときだけ出す。
- **「未計測」と「0 件」を書き分ける。**
- **ファネルの「いちばん落ちている段階」は、素の率どうしで比べない。** 訪問のうち問い合わせ
  ボタンを押すのは数 % が普通、フォームを開いた人のうち送信するのは半分くらいが普通、と
  段階ごとに水準が違う。`thresholds.funnelReference`（目安）に対してどれだけ足りないかで決め、
  画面にも目安を併記する。目安は業種プリセットで変わる。
- **発火 0 件の理由を書き分ける。** 「問題が見つからない」と「まだ診断できていない（連携が無い）」は違う。
- **「データが揃えば判定できる項目」に開発者向けの ID を出さない。** 「GA4 と連携すると、訪問した
  あとの行動を診断できます（判定項目が 47 件増えます）」のように、利用者の行動として書く。

## 28. 決めてもらうこと

| # | 決めること | 選択肢と Claude の推奨 |
|---|---|---|
| 1 | **入口**（いちばん大きい） | **推奨: 既存の Google 連携（OAuth）を第一にし、CSV アップロードは後から足す**。このアプリには GSC / GA4 の連携が既にあり、CSV より取りこぼしが少ない（クエリ取得率の問題も API なら軽い）。ただし §26.8 のとおり「連携できないお客様」が多いという 09-13 の判断とぶつかるので、**この診断は「連携済みの継続コンサル向け」**と割り切るのが素直。逆に「連携は無理。CSV を人が落として貼る」なら CSV を先に作る |
| 2 | **精密診断との関係** | **推奨: 別ツール（`/tools/diagnosis`、仮称「月次診断」）として足す**。見ているもの（サイトの作り vs 数字の動き）が違う。事実シート・検証・履歴の仕組みだけ共有する。「1 つに統合」だと入口の必須項目が増えて、URL だけで動く良さが消える |
